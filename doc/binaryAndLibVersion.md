# 二进制打包版本 与 库版本: (暂时) 最优方案

两件事经常被混在一起, 实际上编号的对象不同:

| | 二进制打包版本 | 库版本 |
|---|---|---|
| 编号对象 | 一次打包产出的二进制 | 一份给别人依赖的源码 |
| 谁关心 | 部署 / 自更新 / 排查线上问题 | 依赖方: 升级会不会坏 |
| 方案 | 本库 (hgmBuildVersion) | url+分支 + 锁 commitId |

## 一、二进制打包版本 —— 用本库

形如 `v0.0.1-260909155041-a1b2c3d4e5-r` = 前缀 (三段) + 打包时刻 + commitId + 干净/脏, 整串是合法的 semver 2.0.0。

需求约束:

- 每次打包自动生成新版本号, 不需要人介入, 不改动 git 内容; 除了 git 仓库和打包机本地以外, 没有任何中心服务管理版本号。
- 不会出现"先用上一个版本号测试, 再改 git 里的版本号文件、commit、重新打包"这种二次 commit。
- 新旧由版本号前缀 (人手改) 和打包时刻决定。
- 拿着版本号就能找到源代码 (commitId), 也能看出打包时间, 不需要另外的服务器记录 "版本号 -> commitId / 打包时间"。

### 附带收益: 升级流程可以全自动真机测试

版本号由打包时刻生成、不需要改 git, 所以测试脚本想要几个版本就打几个, 不需要人介入:

- **同版本代码的升级测试**: 代码不动, 同一份代码打两次, 得到两个版本号, 后打的那个对先打的算升级 (两次落在同一秒时用 `AddTimeSecond` 把后打的挪开 1 秒)。
  用来测"升级流程本身" (下载 / 校验 / 替换 / 重启 / 上报新版本号) 是否正常, 和这次改了什么代码无关。脏工作区也能打, 改了代码不用先提交就能测。
- **新旧版本的升级测试**: 用旧版本发布出去的 zip, 或者用旧版本号里的 commitId 取出旧代码重新编 (注入当年那个版本号原串), 先装上; 再用当前代码打新包, 测从旧版本真的升到新版本。
  用来测"旧版本的升级逻辑能不能接住新版本"。

两种测试的具体步骤见 [usage.md](usage.md) 第四节。

如果改用 commit 时间当序 (见下), 第一种测试做不了 (同一份代码永远是同一个版本号), 脏工作区也测不了。

### 考虑过、没选的

- **semver 手工管理版本号**: 每次发布要人决定版本号、改文件、commit、打 tag; 光看版本号找不到 commitId 和打包时间, 要另查 tag 或包仓库。实际试过, 制造一堆手动工作。
- **用 commit 时间代替打包时间** (Go 伪版本的做法, 同一 commit 永远得到同一个版本号, 利于可复现构建):
  - 同一份代码永远是同一个版本号, 脏工作区打包时 commit 时间也不变, 上面两种自动升级测试的第一种做不了、脏工作区也测不了 —— 本库明确要支持这些。
  - commit 时间不保证递增 (rebase / cherry-pick / 合并老分支 / 提交人电脑时钟), 新包可能比线上的"旧"。
  - 可复现构建的收益目前用不上。
- **"同一 commit 打两次必须是同一个版本号"**: 不做要求 (可以是一个也可以是两个, 例如打包机有缓存)。在"无中心服务"的约束下也没有好办法: 把版本号存进文件又会回到二次 commit / 多个 commit 指向一个版本号的问题, 收益也不明确。

### 和 semver 的关系

- 本库的版本号就是合法的 semver 2.0.0, 样子刻意接近 Go 的伪版本号: `v0.0.1-260909155041-a1b2c3d4e5-r`。`-` 后面的 `时间戳-commitId-脏否` 用 `-` 连成【一个】预发布标识符, 永远不是数字型, 任何取值都合法 (Go 伪版本 `-时间-commit` 也是这样避开前导零的)。
- 比大小 = semver 2.0.0 优先级, 规则一点不改 (`CompareOrder` / `IsUpgrade`, 和 `golang.org/x/mod/semver` 做过差分): 前缀先比, 前缀相同按后缀 ASCII 比, 时间戳定长在最前, 所以就是按打包时刻比; 同一秒的再按 commitId / 脏否分先后 (有先后但没有含义)。
  所以任何 semver 工具比本库的版本号都得到同样的先后, 别的 semver 版本号也可以交给本库比。
- 没用 `+构建信息`: semver 规定它不参与排序, 用了就等于放弃 "每次打包自动得到一个可排序的新版本"; 而且 `+` 进 URL 要转义。
- 前缀三段由人手改, 平时只动最后一段。改后缀格式 / 改时区 / 2099 回绕 / 被错误的大时间戳占住 "最新" 时, 前缀 +1 就够: 旧二进制的 semver 比较器不管新后缀长什么样都判为升级, 不用开新的升级通道。前缀照样可以用来表达兼容性 (不兼容就升前面的段)。
- v0.0.6 及以前的格式是 `v0.1.<时间戳>-<commitId>-<r|d>` (时间戳塞在 patch 段, 前缀两段), 从它迁过来见 [upgradeFromV0.0.6.txt](upgradeFromV0.0.6.txt)。

## 二、库版本 —— url+分支

规则:

- **兼容单位 = url+分支。** 同一个 url+分支 稳定之后不允许较大的 BC (向后不兼容改动)。
- 有较大 BC 时开一个新分支 (在同一个仓库里, 保留 issue / star / 历史), 而不是在老分支上继续改。另开新项目也可以, 但代价更大 (issue / star / 历史 / 搜索排名都分散)。
- **不更新时锁 commitId** (类似 go.sum), **更新时跟 url+分支 的最新 commit**。
- tag 只用来方便人记忆, 不承担其他作用。
  例如本仓库的 `v0.0.5` 是 semver 形式的 tag: 只是给 Go 的 `go get ...@v0.0.5` 和人看用的, 兼容性仍然以 url+分支 为准, 不代表本库在用 semver 管版本。

需要注意的一点 (语言无关):

- 如果同一个程序要同时用到一个库的两个不兼容分支, 分支必须体现在代码的 import 路径里 (或由包管理器映射成不同路径), 否则两边写的都是同一个 import, 只能选一个分支, 另一边就坏了。
  Go 把 `/v2` 写进 import 路径、gopkg.in 把 `gopkg.in/yaml.v2` 映射到仓库的 v2 分支, 都是为了解决这个问题。
- 项目里不会出现这种情况时可以先不管。

### 考虑过、没选的

- **semver 管库版本**: 实际试过, 同样是一堆手动工作 (人判断升哪一段、打 tag)。它的核心价值 "让包管理器在多个版本里自动选兼容的那个", 在 "同一 url+分支 不做较大 BC" 的规则下已经不需要。
- **semver 的其他好处** (在 Go 里 `@latest` 只认 tag、漏洞库按版本范围描述受影响版本、"永不 BC" 实际做不到绝对等) 讨论过, 判断为价值不高或属于特定工具的规则, 不影响上面的选择。
