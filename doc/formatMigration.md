# 版本号格式的升级与废弃

两种情况都会让"已经部署出去的旧二进制"看不懂新版本号:

- 本库的版本号格式改了 (例: 身份后缀从 `-a1b2c3d4e5.r` 改成 `-a1b2c3d4e5-r`)。
- 调用方原来用的是别的版本号格式 (例: 手写的 `1.2.3`), 现在改用本库。

旧二进制里的解析 / 比大小代码是打包时编进去的, 事后改不了。
它的升级闸门按设计"看不懂就不动" (`IsUpgrade` 任一边非法 -> false), 于是新格式的包它一律拒绝 —— 不报错, 静悄悄地谁也不升。

## 一、错误思路: 让旧二进制看懂新格式

- **先发一个"过渡版" (旧格式版本号, 新解析器两种都认), 等全部升上来再切格式**: 多一轮发布, 两步之间必须等所有机器升完, 中间状态难观测。
- **切格式后旧机器人工重装**: 机器一多就不可行。
- **本库解析器永久兼容新旧两种写法**: 格式不再"整串锁死", 同一种东西有两种写法, 每改一次格式就多背一种。

共同的问题: 都在想办法改变旧客户端的行为, 而旧客户端恰恰是唯一改不了的那一方。

## 二、正确思路: 升级通道本身带一个数字版本号, 服务端按对方的通道版本说它听得懂的话

客户端改不了, 服务端 (下发更新的那一方) 随时能改。所以兼容工作全部放在服务端:

1. **升级通道有一个数字版本号** (下称通道版本), 和版本号格式无关, 每次升级协议 / 版本号格式不兼容地改动时 +1。
   - 请求类接口 (查询有无更新 / 探测 / 下载): 请求里带一个数字字段。旧客户端不发这个字段 -> 收到零值 -> 当最旧的通道。
   - 广播 / 订阅类 (服务端一对多推"有新版本"): 一份广播没法对不同对端说不同的话, 所以通道版本要体现在**频道名**里 (例 `xxx/update2` -> `xxx/update3`), 新旧客户端天然订阅不同的频道, 服务端各发各的。
2. **服务端对旧通道做"降格"**: 把真实版本号转换成旧通道认识的某一个版本号再给出去; 旧通道发回来的版本号, 先转回真实版本号再处理。
3. **旧客户端照常走它自己的升级流程**, 拿到的是它看得懂、且比它当前版本"更新"的串, 于是正常拉包、替换、重启。
4. **新二进制起来后自报真实版本号** (运行期只从本库的 `hgmBuildVersionCurrent.GetCurrentVersion()` 取), 改走新通道, 下次比对相等 -> 收敛, 不会重复升级。
5. **全部客户端升上来之后** (要有库存 / 上报能看到每台的版本号), 删掉降格代码和旧通道的处理分支。
   旧频道名**不要回收再用**: 名字一复用, 就可能再遇到一次"旧客户端挂在旧名字上收不到广播"的问题。

### 降格要覆盖旧客户端升级流程的【每一个】接触点

逐个列出旧客户端在升级过程中会把版本号交给服务端、或从服务端拿版本号的地方, 一个都不能漏。典型的有:

| 接触点 | 服务端对旧通道的处理 |
|---|---|
| 广播 "有新版本" | 旧频道发降格后的串, 新频道发真实串, 两个频道同时发 |
| 查询有无更新 | 先把对方报来的当前版本号转成真实格式再判 `IsUpgrade`; 回给它的目标版本用降格后的串 |
| 探测 / 下载二进制 | 收到降格串 -> 转回真实版本号 -> 找真实的包 |
| 升级后的自检 / 对齐 | 一般比的是新二进制自报的整串, 不受影响; 但要逐个核对旧代码里有没有"拿请求时的版本串去和新二进制自报的串比 ==" 的地方 |

### 转换的要求

- **新 -> 旧必须保序**: 降格后的串, 在旧客户端的比较规则下, 要比它当前的版本"更新"; 同一批真实版本降格后先后不变。
- **旧 -> 新必须能找回**: 服务端要能把旧通道发来的串还原成真实版本号。
  能纯函数互转最好 (例: 只差一个分隔符, `-r` <-> `.r`), 不用存映射表; 做不到就由服务端存一张 "降格串 -> 真实版本号" 的表。
- 降格串只是旧通道上的**传输令牌**, 不进新二进制、不落新客户端的配置, 只活在服务端的兼容代码里。

### 本库自己的立场

- 本库的解析器**只认当前格式**, 不兼容历史格式。历史格式的解析 / 转换写在服务端的降格代码里, 随旧通道一起删。
- 本库不提供拆段的函数 (见 design.md "不透明字符串"); 降格时需要的那点拆解属于一次性的兼容代码, 由服务端自己写。

## 三、调用方从别的版本号格式迁过来

迁移后的新二进制里, 判断升级要包一层: 当前版本是旧格式时, 本库的 `IsUpgrade` 一律 false。
通常只需要 `IsValid`, 不需要拆本库版本号的内部字段:

```go
func isUpgrade(cur, target string) bool {
	if hgmBuildVersion.IsValid(cur) {
		return hgmBuildVersion.IsUpgrade(cur, target) // 新 -> 新; target 是旧格式时自然 false (不许降回旧格式)
	}
	if isLegacy(cur) && hgmBuildVersion.IsValid(target) {
		return true // 旧 -> 新: 切换格式之后打的包, 一定比所有旧格式的包新
	}
	if isLegacy(cur) && isLegacy(target) {
		return legacyIsUpgrade(cur, target) // 旧 -> 旧: 原来的规则
	}
	return false // 看不懂就不动
}
```

"切格式之后的包一定比旧格式的包新" 这条事实只有调用方知道, 所以这一层写在调用方, 不进本库。

已经部署出去的旧二进制, 它的旧比较规则遇到本库的版本号怎么判, 取决于旧规则 (例如 semver 比较很可能认为 `v0.1.260909155041-...` 比 `2.5.0` 旧)。
有升级通道的, 同样走第二节的通道版本 + 降格: 服务端给旧通道一个按旧规则"更大"的旧格式串, 下载时再映射回真实的包。
没有远程 / 自升级流程的, 不存在这个问题, 直接切换即可。
