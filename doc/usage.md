# hgmBuildVersion 实战用法

API 见 `../readme.md`。这里写的是"一个会自更新的程序, 版本号相关的事情具体怎么做", 都是在实际项目里跑通过的做法
(多平台 agent + 一个中心服务, agent 由中心推送自更新; 真机 linux + windows 自动测试)。照着做就行, 不用再自己做决策。

## 一、打包侧

### 1. 一次打包只生成一次版本号

```go
ver, err := hgmBuildVersion.NewBuildVersion("versionPrefix.txt") // 正式发布用 NewReleaseVersion, 见下
// 每个平台 / 每个二进制都用这同一个 ver:
exec.Command("go", "build", "-ldflags", "-X "+hgmBuildVersionCurrent.GetVersionVarFullName()+"="+ver, "-o", out, pkg)
```

- 同一次打包出来的所有东西 (各平台二进制、zip 文件名、zip 里的 version.txt、中心服务配置里的"最新版本") 用的都是这一个 ver。
  打包函数开头取一次, 往下传; 不要每个 target 各取一次 (跨秒就是两个版本号)。
- 打包工具【不提供】`-Version` 参数。"升一版" = 再打一次包 (再生成一次)。
  唯一的例外是第四节"重新编一个旧版本": 那时注入的是【当年记录下来的那个版本号原串】, 不是人手编一个。
- 不要在版本号上做算术 / 拼接 / 推算下一个版本, 也不要自己拆它。只能原样传递、`==` 判等、交给本库。

### 2. 包里放什么

- zip 文件名和 zip 里的顶层目录都带版本号整串, 例 `myApp-v0.1.260909155041-8d8358905d.r.zip`。
  文件名只给人看, 程序不从文件名里取版本号。
- zip 里放一个固定文件 `version.txt`, 内容就是版本号整串 (一行, 和 `version` 子命令的输出一样)。
  ★程序要知道"这个 zip 是哪个版本"时, 一律读它, 不解析文件名: 读出来 -> `IsValid` -> 拿去比新旧 / `GetCommitId` 找源码。
- 如果有中心服务负责分发, 它的配置里写"当前发布版本 = 这个 ver", 由安装包自己带过去, 不让人手填。

### 3. 正式发布用 `NewReleaseVersion`

```go
ver, err := hgmBuildVersion.NewReleaseVersion("versionPrefix.txt")
```

工作区不干净 (结果会是 `.d`)、或者 HEAD 还没推送到远端时直接返回 error。这样发出去的每个包, 拿着版本号一定找得到准确的源码
(有 git 子模块时不完全成立, 见 [design.md](design.md) 的"已知限制")。
开发测试打包继续用 `NewBuildVersion` (脏工作区照样打)。

"已推送"看的是本地的远端跟踪分支 (`git branch -r --contains HEAD`), 不联网: 先 `git push`, 再打包。

## 二、运行侧

### 1. 取自己的版本号: 只有一个来源

```go
cur := hgmBuildVersionCurrent.GetCurrentVersion()
```

- 全程序只从这里取。不要在 main 包或别处再声明一个版本变量, 也不要再单独注入 commitId / 脏否 (它们已经在版本号里)。
- 开发机直接 `go build` 没注入时是空串。【保持空串】, 不要造 `v0.0.0` 之类的哨兵:
  空串天然 `IsValid()==false`、天然赢不了任何一次 `IsUpgrade`, 开发版本永远不会被当成可以升级 / 可以分发的版本。
- 如果某个配置文件里也存了"当前版本" (例如 agent 的配置), 启动时用二进制自带的版本号覆盖它 (二进制没注入时才保留配置里的值, 方便本地调试):

  ```go
  if v := hgmBuildVersionCurrent.GetCurrentVersion(); v != "" {
      cfg.Version = v
  }
  ```

  ★这是自更新能【收敛】的关键: 换了二进制之后"当前版本"必须跟着变, 否则和"最新版本"比永远是旧的, 会无限自更新。

### 2. 升级闸门: 默认和自动触发过 `IsUpgrade`, 人手操作可以强制

```go
if force || hgmBuildVersion.IsUpgrade(cur, latest) {
    // 拉新二进制 -> 校验 -> 替换 -> 重启
}
```

- 自动触发点通常有两个, 都必须过 `IsUpgrade`, 不能有任何一处用 `!=`:
  1. 中心推送"有新版本" (实时事件 / 广播, 载荷就是版本号原串);
  2. 程序启动后主动问一次中心 (不轮询)。
  中心判过一次、客户端收到后【再判一次】: 多个触发点共用同一个"执行升级"函数, 闸门放在客户端那一处最不容易漏。
- 自动触发时同版本 / 降级 / 版本号看不懂 一律不升: 同版本也升 = 每次触发都升 = 无限自更新; 降级不升 = 防误操作 / 回滚攻击。
- 人在机器上敲的手动更新 / 覆盖安装命令: 默认同样过 `IsUpgrade`, 但【留一个强制选项】(例 `-Force`) 跳过它,
  用于 重装同一版本修复损坏的安装、临时换到某个旧版本排查问题 之类。
  - 强制只跳过 `IsUpgrade`, 【不跳过 `IsValid`】: 版本号要当路径 / 嵌进脚本, 看不懂的版本号强制也不放行。
  - 强制降级只是暂时的: 中心的"最新版本"还是新的那个, 下一次自动触发就会把它升回去。
- 想让【全场】回到旧代码: 不用强制。在 git 里 checkout 旧 commit (真正的 git 工作区, 不是 archive 出来的目录),
  用 `NewReleaseVersion` 重新打一个包 —— 时间戳更新, 序更大, 旧代码走正常的自动升级通道下发到所有机器。
- 手动更新命令可以额外比文件内容 (大小 + MAC): 已经是那一版就一个字节都不传。

### 3. 版本号当路径 / 嵌进脚本: 入口处先过 `IsValid`

版本号会从外部进来 (网络请求、中心下发的配置、zip 里的 version.txt), 凡是要把它:

- 当目录名 / 文件名 (例 中心暂存各版本二进制的 `downloads/<版本号>/<os>_<arch>`),
- 拼进 http 路由,
- 原样嵌进生成的 sh / powershell 脚本,

都在【进入本机的那个入口】过一次 `IsValid`, 不合法就当没有 / 直接报错。
合法版本号的字符集锁死在 `[0-9a-zA-Z.-]`, 不会路径穿越、不会注入; 但拼 URL / 拼 shell 时照常转义。

★当目录名用【整串】, 不要只取前面的序: 同一秒打的两个不同 commit 的包序相同, 只取序会撞进同一个目录互相覆盖。
写入和读取 (暂存、分发、http 路由) 必须是同一个口径。

### 4. "是不是这一个包": 用整串 `==`

以下判断都是比【身份】, 用整串相等, 不用 `IsUpgrade`:

- 部署工具确认"目标机上跑的就是我刚打的那个包": 让远端二进制自报版本号 (`version` 子命令), 和本次打包的 ver 整串比。
  ★不要看子命令的退出码: 很多命令行框架遇到不认识的子命令是打帮助然后正常退出, 老二进制会"成功地什么都没做"。
- 一键安装脚本"本机已有的二进制是不是正好是要装的那一版": 是就直接复制它, 不用再下载几十 MB。
- 一个程序的两个部件 (例 windows 上的服务进程和它的辅助进程) 互相确认是不是同一版, 不是就把旧的那个换掉。
- 自动测试断言"所有机器都升到了这一版"。

## 三、版本号显示在哪里

| 位置 | 内容 |
|---|---|
| `xxx version` 子命令 | 一行, 就是版本号整串, 没有别的字。人读和脚本读是同一条路 (脚本拿整行去 `==`)。没注入时是空行。 |
| zip 文件名 / zip 顶层目录 | 带版本号整串 (给人看) |
| zip 里的 `version.txt` | 版本号整串 (给程序读) |
| 客户端上报给中心的库存 | 每台机器的当前版本号 (来自二进制自身) |
| 中心的查询接口 / 管理网页 | 中心自己的版本号 + 每台机器的版本号, 原样显示 |
| 服务启动日志 / 自更新日志 | 启动时打一行自己的版本号; 自更新时打 "当前=.. 目标=.." |

线上出问题时: 从上面任何一处拿到版本号 -> `GetCommitId` (或者人眼看) 取出 commitId -> `git checkout <commitId>` 就是那份代码。

## 四、升级的真机自动测试

两种测试都是全自动的, 不需要人改任何文件、提交任何东西。测试过程中只做"部署新版本的中心服务"这一个动作,
之后不对客户端做任何操作: 升级必须由客户端自己收到更新事件并完成, 测试只等结果。

### 1. 同一份代码的升级测试 (常设, 每次都跑)

测的是"升级流程本身" (推送 / 下载 / 校验 / 替换 / 重启 / 重新上线 / 上报新版本) 是否正常, 和这次改了什么代码无关。
这条断了的线上表现是"发了新版本, 所有机器一动不动, 没有任何报错", 单元测试够不着。

1. `base := NewBuildVersion(..)`, 用它首装中心服务和客户端, 等所有客户端上线且版本号 `== base`。
2. `next := NewBuildVersion(..)` (同一份代码再生成一次), 先断言 `IsUpgrade(base, next)`:
   两次打包落在同一秒时它会失败, 这时测试应当直接报错, 而不是往下跑一个必然超时的等待。
3. 用 `next` 重新部署中心服务。
4. 不碰客户端, 等所有客户端上线且版本号 `== next` (给足时间, 例如 4 分钟; 超时即失败)。
5. 断言升级的副作用: 身份没丢、配置没丢、升级不该重启的东西没被重启。

脏工作区也能跑: 改了代码不用先提交就能测升级。

### 2. 从旧版本升到新版本的测试 (每次发版前跑)

测的是"线上正在跑的那个旧版本, 它冻住的升级代码能不能接住新版本"。风险恰恰在旧二进制身上:
它连不上新中心 = 全场失联, 而且没有远程补救。所以旧的那一版必须是当年那个 commit 编出来的真东西, 装法也必须是旧代码自己的装法。

测试里只写死一个常量, 每次发版之后改成新的线上版本:

```go
const oldVersion = "v0.1.261001101926-e0ba4f37f7.r" // 线上机器自报的那一串 (或者旧 zip 里 version.txt 的内容)
oldCommit, ok := hgmBuildVersion.GetCommitId(oldVersion) // 不要另抄一份 commitId 常量
```

拿到旧版本有两种办法 (本库不提供, 下面是建议做法):

- **直接用当年发布的 zip** (见第五节, 从 GitHub release 下载): 最简单, 而且就是线上那个包本身。
  读 zip 里的 `version.txt` 确认它就是 `oldVersion`。
- **从 git 重新编旧版本**:
  1. `git archive <oldCommit>` 解到临时目录。有 git 子模块的话, 用 `git ls-tree <oldCommit> <子模块路径>` 取出旧 commit 里钉的子模块 sha,
     再到各子模块仓库里 `git archive <sha>` 解到对应位置。
     不用 `git worktree add`: 那样子模块是空目录。
  2. 在旧代码树里跑旧代码自己的代码生成 / 构建工具。
  3. 版本号【直接注入 `oldVersion` 原串】(`-X ...=oldVersion`), 不要在旧代码树里调 `NewBuildVersion`:
     archive 出来的目录没有 `.git`, git 会一路往上找到外面的新仓库, 编出来的"旧版本"自报的是新 commit 和现在的时间。
     注入原串之后, 编出来的旧包和线上那一版的版本号完全一样。
  4. 旧代码树按 commit 缓存在临时目录里 (同一个 commit 的代码不会变), 不必每次重新解压和生成。

流程:

1. 新版本 `next := NewBuildVersion(..)`, 先断言 `IsUpgrade(oldVersion, next)`。
2. 清场, 用旧 zip / 旧代码装中心服务和客户端, 等所有客户端上线且版本号 `== oldVersion`。
3. 用当前代码部署新版本的中心服务, 断言中心自报 `== next`。
4. 不碰客户端, 等所有客户端版本号 `== next`。
5. 断言: 身份 / 信任关系 / 配置 / 已有的服务进程在升级前后不变。

## 五、GitHub 发布线上包 (一个 zip)

### 1. 发布

- **对外发布时, 人认为一个前缀才是一个版本**: 一个前缀 (`versionPrefix.txt` 的内容, 例 `v0.4`) 只往 GitHub 发布【一次】,
  一个 tag、一个 release、一个 zip。版本号后面的时间戳和 commitId 只用来找打包时间和源码, 不是给外部用户区分版本用的。
- 下一次对外发布 = 先把 `versionPrefix.txt` 升一级 (例 `v0.5`) 并 commit + push, 再用 `NewReleaseVersion` 打包、发布。
  同一个前缀下内部打的那些包 (时间戳不同) 只在内部分发 (第二节的中心推送), 不上 GitHub。
- 正式打包 (`NewReleaseVersion`) 出来的 zip, 文件名带完整版本号, 作为这个 release 唯一的附件:

  ```sh
  gh release create v0.4 --target "$commitId" --title v0.4 --notes "..." "bin/myApp-$ver.zip"
  ```

  `--target` 填打包时的完整 commitId (`git rev-parse HEAD`), 让 tag 正好指向打包的那个 commit; 不填时 GitHub 用默认分支的最新 commit 建 tag, 不一定是打包的那个。
- 一个 zip 包含所有平台, 和内部分发用的是同一个包, 不另打一份。
- 除了这个 tag 以外, 发布不往 git 里写任何东西。找源码以 zip 里的版本号 (`GetCommitId`) 为准, tag 只方便人记。
- `v0.4` 这种两段的 tag 不是 Go module 认的版本格式 (要三段), 仓库同时是 Go module 时也不会混进 module 的版本列表。

### 2. 客户端从 GitHub 拿最新版本

```
GET https://api.github.com/repos/<owner>/<repo>/releases/latest
  -> tag_name / assets[]: name / browser_download_url
```

1. 取最新 release 里的那个 zip (每个 release 只有一个 zip 附件), 下载。
2. 校验完整性 (例如用自己的密钥对包算 MAC; 不要只靠 HTTPS)。
3. 读 zip 里的 `version.txt` -> `IsValid` -> `IsUpgrade(cur, 它)` 为真才安装 (或者人手 `-Force`)。
   "最新 release" 只是 GitHub 那边的顺序, 最终闸门还是 `IsUpgrade`: 有人误把旧包标成了最新, 客户端也不会跟着降级。

### 3. 拿某个版本的源码

拿到 zip -> 读 `version.txt` -> `GetCommitId` -> `git checkout <commitId>` (或 `git archive`)。
第四节"从旧版本升到新版本"的测试, 旧 zip 就是线上那个前缀的 release 里唯一的那个 zip。
