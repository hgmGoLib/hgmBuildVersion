hgmBuildVersion —— 升级流程 + 对接检查点
======================================================================

用到本库做升级的项目, 照第一节的流程对接, 对接完照第二节逐条核一遍, 以后改升级代码时再核一遍.
API 见 ../readme.md, 打包 / 显示 / 测试的具体写法见 usage.md.


一、流程: 只分两种升级
------------------------------------------------------------

1. 服务端升级 (自己的服务 / 集群, 运维拿着一个包去升)

   - 旧代码只做一件事: 解压包, 然后立刻运行包里的新程序. 升级由新程序来做.
   - 新程序默认只允许 "旧 -> 新": 逐个看线上实例, 用 IsUpgrade(线上版本, 包的版本) 判,
     有一个不是严格更旧 (同版本 / 比包新 / 版本号看不懂) 就拒绝, 报错里写出是哪台哪个版本.
   - 只有一个 -force: 加了就跳过上面所有版本检查, 无条件放行 (同版本重装 / 降级 / 看不懂的版本号都放).
     不拆成多个跳过参数.

   这里用比较器没问题: 做判断的是新程序, 它是你刚写的, 认不认识旧版本号、认不出时怎么办, 随时能改.
   判错了也有 -force 兜底.

2. 客户端升级 (装在别的机器上、自己更新自己的程序: agent / CLI / 桌面端 ...)

   - 客户端通过 rpc 上报: 当前版本号 (原样, 可能是空串 / 旧格式) + 设备号.
   - 服务端决定升不升、升到哪个版本. 怎么决定随服务端: 读配置、查数据库、按设备号灰度 / A/B、
     回滚、版本号格式变了怎么认, 都写在服务端. 服务端要比新旧就用本库的 IsUpgrade / CompareOrder.
   - 服务端回: 目标版本 + 下载地址 + 包的 sha256 (或签名).
   - 客户端只做: 目标为空, 或者和自己的版本号整串相等 -> 不动; 否则下载、校验、替换、重启.
     客户端【不比新旧】, 也不加别的兜底 (退避 / 失败计数 / 自报版本校验 ...).
   - 服务端主动推送 (广播 / 订阅) 只发 "去问一下", 不带目标版本. 客户端收到后走上报那一步.
     (广播没法按设备区分; 广播里带版本号, 客户端就得自己判, 又回到老问题.)
   - 升级接口可以改: 服务端保留旧接口给还没升上来的旧客户端, 库存里看不到旧客户端了再删.

   为什么客户端不许比新旧: 比较器编进客户端就冻住了, 部署出去改不回来. 以后版本号格式一变,
   旧客户端看不懂新版本号 -> IsUpgrade 判 false -> 静默不升, 只能在服务端伪造 "旧客户端眼里更大" 的串
   (formatMigration.md 第二节那一套), 每改一次格式来一遍. 放到服务端判, 格式怎么改都只改服务端.
   它原来声称的收益也不成立:
     - "同版本不升, 防无限自更新": 整串 == 就够了.
     - "防回滚攻击": 客户端只信认证过的服务端, 服务端被拿下了直接推恶意新版本就行, 用不着推旧版.
       包的完整性靠 sha256 / 签名, 不靠版本号.
     - "防误操作降级": 服务端把目标改成旧版本, 就是想回滚. 客户端拦它, 等于把正当回滚变成逐台人工重装.

   下面两条是原来就有的, 换成这套流程照样要守:
     - 客户端的 "当前版本" 只从 hgmBuildVersionCurrent.GetCurrentVersion() 取: 换了二进制它就跟着变,
       升级才会收敛. 从配置文件 / 当年装机时记下的值取, 会永远和目标不相等, 无限升级.
     - 版本号要当路径 / 拼进脚本, 入口处先过 IsValid (见 usage.md 二、3). 这和新旧无关, -force 也不跳过.


二、检查点
------------------------------------------------------------

A. 代码 (审查 / grep)
   A1  会自更新的客户端二进制里, 不调 IsUpgrade / CompareOrder (含复制进客户端的 ts/hgmBuildVersion.ts).
   A2  客户端的升级判断只有一处, 写法就是 `target != "" && target != cur`.
   A3  推送 / 广播的载荷里没有给客户端做判断用的版本号.
   A4  客户端的当前版本只来自 hgmBuildVersionCurrent.GetCurrentVersion().
   A5  服务端升级只有一个 -force, 加了就跳过全部版本检查.
   A6  客户端没有本地的 "防降级" / "版本递增闸门" / 失败退避之类分支.

B. 自动测试: 客户端升级 (真进程, 不碰客户端, 只动服务端, 等客户端自己升)
   B1  固定的真实旧版本客户端 (当年发布的包, 或用当年 commit 重编并注入当年的版本号原串, 见 usage.md 四、2)
       -> 服务端把目标指到新版本 -> 等客户端自报 == 新版本 -> 再问一次服务端, 回 "不用升".
   B2  服务端把目标指到一个比客户端更旧的版本 -> 客户端真的降过去.
       (证明客户端里没有残留的新旧判断. 这条不能省.)
   B3  服务端目标 == 客户端当前版本 -> 客户端不动.

C. 自动测试: 服务端升级
   C1  旧 -> 新, 不加 -force: 成功.
   C2  新 -> 旧、同版本、线上版本号看不懂, 不加 -force: 都被拒绝.
   C3  C2 那三种加 -force: 都放行.

D. 过渡 (每个项目只做一次)
   已经部署出去、客户端里还在调 IsUpgrade 的旧版本: 服务端在旧接口上给它们的目标版本必须在它们眼里 "更新"
   (正常新打的包本来就是; 不是的情况见 formatMigration.md). 新客户端铺开、库存里看不到旧版本之后, 删掉旧接口.


三、走偏的典型 (看到就改回来)
------------------------------------------------------------
- 客户端里加 "防降级" / "防回滚攻击" 的新旧判断.
- 客户端里加退避、失败计数、装完校验自报版本之类的兜底分支: 平时走不到、测不到, 真出事时最可能出 bug.
  真循环升级了, 服务端的日志 / 库存一眼能看到, 改服务端.
- 服务端的决定被限制成 "只能按某个固定规则算": 服务端怎么决定没有任何约束.
- -force 拆成好几个跳过参数.
- 为了让旧客户端看懂新格式, 开通道版本 / 降格 (只有第二节 D 的过渡期才需要).
- 版本号格式改了以后服务端升级闸门判错: 不用改流程, 用 -force 升这一次, 或者把 versionPrefix.txt 的前缀 +1.
